Glossary (each term once): **gauge R&R** — a metrology study that splits an instrument's spread into repeatability (same conditions,
repeated) and reproducibility (conditions deliberately changed) and compares the total, as **%GRR**, with the spread of the items
being measured; **ndc** — the number of distinct item levels the instrument can separate. **Run-to-run variability** — the same
nominal configuration run twice gives different outputs; **parallel variability** — environments inside one batch, started
identically, give different outputs (GPUSimBench's two metrics). **Atomics** — GPU additions by many threads into one memory cell,
whose order is set by the scheduler; floating-point addition is not associative, so the sum depends on the order. **RUN_TO_RUN** —
Warp's deterministic mode, which records atomic updates and reduces them in a fixed order. **Frozen policy** — a fixed checkpoint run
with deterministic actions.

## 3. The two closest papers' limitation text (verbatim, grep-verified)

**GPUSimBench 2607.13059, sec. VII Conclusion and Limitation:** "This work has several limitations. First, GPUSimBench currently
covers only a limited set of tasks and metrics, and the conclusions should be interpreted within this benchmark scope. Specifically,
we evaluate two scalability scenes and one contact-rich real-world-matched experiment, all on a single hardware and software stack.
As a result, the reported performance and variability may change across different GPUs, drivers, and simulator versions." **Sec.
VI-A:** "In all inclined-collision runs, we fix random seeds and disable all task-level randomization, so any observed variability
reflects numerical and execution-level effects rather than intentional stochasticity." **Type 2:** "Both metrics are reported as
0.00 ± 0.00 in Table IV. In our benchmark, this means that the results are indistinguishable between parallel environments and
between independent runs at the reported precision". **Sec. VI-C:** "If your workflow involves contact-parameter tuning, design
comparisons, or reporting averaged sim-to-real outcomes across repeated runs, additionally prioritize low Run-to-Run Variability in
Table IV to reduce confounding from solver path drift". **Sec. V:** "We use $N_{\text{env}} = 16$ parallel environments per
simulator run".

**2609.34666, sec. IV Conclusion:** "This work is limited to TaiChi-based differentiable MPM implementation and observations
collected by two motions (pressing a playdough and scooping a box of sand). Future investigation should be extended to other
differentiable programming languages and more diverse contact processes." ... "AD/FD checks should test several perturbation sizes
and compare the resulting perturbation-induced loss changes with repeated-forward loss variation; a finite-difference estimate is a
weak reference when these quantities are of similar magnitude".

**Owners' pages.** Newton: "By default, a Newton simulation on the GPU is not bit-for-bit repeatable: two runs from the same initial
state with the same inputs usually agree to a few units in the last place at first and then drift apart"; "Use it for regression
tests, debugging, reproducible training and data generation, and replays that must match a recording." Isaac Lab: "Given the same
hardware and Isaac Sim (and consequently PhysX) version, the simulation produces identical results for scenes with rigid bodies and
articulations"; PR #7334: "PhysX is run-to-run deterministic for rigid bodies"; the Newton MJWarp default is
`deterministic_mode="not_guaranteed"`.

## 4. Why has this not been done

The measurement (engine-only spread of a frozen policy's return against reported gaps) is a one-day job and nobody has run it
because the owners chose removal over measurement: three engines shipped deterministic modes between August and November 2026
(Isaac Lab #6930 2026-08-06 and #7334 2026-08-25; Warp 1.19 and Newton #5041 2026-11-03; MuJoCo Warp `DeterminismType` with ordering
2026-11-08), each justified by regression testing and replay, not by policy comparisons. The enabling piece for a clean measurement is
exactly those modes (a bitwise zero arm at a stated cost), and it is weeks old; the piece that would make the headline true — a
configuration-level shift that does not average over episodes — has no datum for or against it in return units. For the per-episode
component the answer is "it is not a floor because the reported statistic averages it", which is why evaluation-statistics owners
(Colas, Agarwal) never carried it as a separate term.

## 5. Killing experiment check

**P-W43-09-lit as written** ($0, two days): tabulate twenty papers' reported gains and seed intervals beside "the engine's measured
run-to-run / batch-slot divergence (GPUSimBench numbers where the engine matches)". GPUSimBench's numbers are centimetres of cube
displacement on one passive scene at $N_{\text{env}}=16$; the papers' gains are returns or success rates over randomised resets at
$N_{\text{env}}$ in the hundreds or thousands; the third column has no entry comparable with the first. The table cannot be filled from
print at any cost; the probe fails Gate 1 and is a sketch. **The import's gauge study** (<30 GPU-h) is under one GPU-week but
measures the wrong level: repeatability over 10 repeats at fixed state is $\sigma_\omega$ per episode, part variation is the spread of
checkpoint means, so %GRR is not the share of anything a paper reports. **What the claim's survival would have required:** a
measured configuration-level term $b_\pi(c)$ — the shift of $\hat J(\pi; c)$ with batch size $\{256, 1024, 4096\}$, slot permutation and
GPU model at $N$ large enough that $\sigma_\omega/\sqrt{N}$ is under 1% of return — exceeding the paper's own seed interval on a Type 1
or Type 3 engine, with the deterministic mode as the zero arm and the CPU engine as the bias reference; pre-registered kill: every
$|b_\pi(c)|$ inside the seed interval. Cost about one GPU-day on three Isaac Lab or Playground checkpoints. Design hints for 6d:
report $\sigma_\omega$, $b_\pi(c)$ and the seed interval as three rows of one decomposition; pair policies by event-keyed random numbers
(2603.11084) if a paired design is used; state the dtype floor (float32, checklist 2026-10-20); run the deterministic mode's
wall-clock cost beside it, because that cost (9–48x in Newton's own numbers) is what the owners will ask.
