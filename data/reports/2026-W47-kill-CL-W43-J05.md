Glossary (each term once). **Physics engine** — the library that advances a robot scene one time step: contact detection, a
constraint or contact solver, integration. **GPU-native engine** — one written for the GPU from the start (MuJoCo Warp, Newton,
Genesis, Isaac, MJX); **CPU-era code** — a library written for one CPU core, often in Python or Fortran loops. **Kernel** — one GPU
or CPU routine that does one stage of the step. **Speedup $s$** — reference time over candidate time, $s = t_{\mathrm{ref}} /
t_{\mathrm{cand}}$, on the same inputs and hardware. **Geometric mean** over $n$ kernels — $\bar s = (\prod_i s_i)^{1/n}$, the
average that does not let one 99-fold kernel carry the rest. **Fixed accuracy** — the candidate's output must pass a stated
numerical test before its time counts. **Reference-match oracle** — the test is agreement with the incumbent's output to a
tolerance; **physics oracle** — the test is a property of the answer itself (energy drift, convergence order, a residual).
**Keep-or-discard loop** — an agent proposes one code change, the harness measures it, the change is kept only if the metric
improves and every gate passes. **Reward hacking** — the agent raises the measured number without doing the work (hard-coded
outputs, skipped iterations, timers moved). **Adversarial reviewer** — a second agent that searches, by executing inputs, for a
case where the candidate's output differs from the reference. **Hot path** — the stage that takes most of the step time.

## 3. The closest papers' own limitation and protocol text (verbatim, grep-verified)

**2611.13143, Discussion.** "The kernel gains measure the room left in ASE's Python code (four of the six kernels loop over atoms;
Methods), not the distance to the fastest possible implementation. Compiled code goes further (Fig. 2). Much scientific code is
written in high-level languages, and agents can recover such room on their own under checks they cannot alter." ... "With three
runs per configuration, comparisons are descriptive, and differences below about 10–15 % are invisible." **Methods, gate:**
"which admits floating-point reordering and rejects a single-precision downgrade." **Results:** "The adversarial reviewer caught 51,
including a k-d-tree pair search, 7.75 times faster, whose output differed from stock ASE's on rank-deficient periodic cells."
**Discussion:** "a numeric check on fixed systems is necessary but not sufficient, and an adversarial reviewer that had to execute
its counterexample caught most kernel defects." No limitations section exists; the Discussion paragraph above is it.

**2609.35639, sec. 3.2 and App. C.** "Any computational strategy is allowed as long as it meets these accuracy requirements." "Each
tolerance is set above the variation between correct FP32 implementations, which differ in rounding, reduction order, and the order
of atomic accumulation, and well below the effect of plausible implementation errors". "Linear and Newton solves instead require the
true residual of the returned solution to fall below the prescribed solver tolerance." **Results:** "no submission is more than 5%
faster than the reference"; "The largest gaps arise in collision detection, constraint solving, and iterative solvers"; "Most of
these are single memory-bound passes that the reference already runs close to peak memory bandwidth, leaving little room to improve
on it." **Budget ablation:** "The default budget is rarely binding: at 1.0×, Opus and GPT use a median of 43% and 50% of it and never
reach the deadline". The brief's reading "GPUPhysBench defines correctness as matching expert code" holds for most tasks (relative
$\ell_2$ against the reference) and not for the solves (true residual) — the oracle is mixed, and the residual half is a physics
oracle.

**2611.10378, Results and Conclusions.** "The original and optimized simulations produced identical trajectories for both systems,
but the optimized version reduced the total simulation time by 19–22%". "On a single CPU thread, the optimized implementation
reduced the total MD time by approximately 1 to 2 orders of magnitude compared to the original implementation. This result
indicates that a significant portion of the performance gain is attributed to code re-factorization rather than to parallel
execution alone." "As the optimization task became more expansive and less well-defined, it required more human scientific
expertise and guidance."
