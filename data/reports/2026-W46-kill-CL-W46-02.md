Glossary (each term once). **litellm** — a Python layer that takes an OpenAI-format chat request and rewrites it into each
provider's own request format, returning a normalised reply. **Native SDK** — the provider's own client library speaking the
provider's own format. **OpenAI-compatible endpoint** — a provider-run server that accepts OpenAI-format requests and translates
them on the provider's side (Google runs one for Gemini). **isloss / ConvIR** — the oracle of 2611.15543: both the source
request and its translation are mapped to one intermediate representation and rules flag information the target format could
have carried but the translation dropped ("avoidable loss"). **Tool-bearing request** — a message list carrying at least one tool
call and tool result. **Replicate floor** — the spread between repeated runs of one arm with every setting fixed. **drop_params** — a litellm switch that silently removes request fields the target
provider does not accept.

## 3. The two closest papers' limitation text (verbatim, grep-verified against the fetched HTML)

**2611.15543 isloss, sec. 7.1 Implications for translators and model evaluation.** "Second, translation is a potential confounding
factor in model evaluation. When a benchmark or agent framework routes requests through a shared translator, the model may
receive a prompt, tool specification, or generation configuration that differs from what the benchmark intended. Changes to
system-instruction authority, tool schemas, and error flags can therefore affect the conditions under which models are evaluated
... This concern is relevant to benchmark pipelines such as $\tau$-bench (Yao et al., 2024) and BFCL (Patil et al., 2025) whenever
they rely on LiteLLM, the Vercel AI SDK, or other translation layers." ... "Our captured translations and field-dependent
behavioural experiments demonstrate that translation-induced changes can alter model behaviour; the GSM8K control also shows that
such effects are task-dependent. However, we have not measured the resulting changes in published benchmark scores or leaderboard
rankings. Establishing their impact on end-to-end benchmark comparisons remains an important direction for future work." **Sec.
7.2 Threats to validity.** "Our findings are specific to the payloads observable at the selected capture points. Changes introduced
after the last instrumented translation boundary, including provider-side rewriting, are not necessarily visible to isloss." ...
"The live-model experiments cover selected field-dependent mechanisms and tasks rather than the full range of model behaviour.
Their results establish that particular translation changes can affect particular measured outcomes under the tested conditions;
they do not imply that every detected information loss will change model behaviour." ... "We did not inspect commercial hosted
gateways or the compatibility layers operated by Anthropic and OpenAI. Google's OpenAI-compatible Gemini endpoint is the only
first-party compatibility endpoint for which we conducted external behavioural probes." **Sec. 6.2:** "This negative result is
important: the observed effects depend on the information affected and the task being tested; not every translation change
necessarily produces a measurable degradation on every downstream task." **App. B.1 (Table 14):** "LiteLLM (1.103.1 / 1.103.2,
drop_params=False)".

## 4. Why has this not been done

The enabling piece is the oracle (2611.15543, 2026-11-11), and its authors wrote the measurement into their future work with the
benchmark named. The second enabling piece — a serving-adapter-only contrast on a tool-use benchmark with the funnel instrumented —
is 2609.03966 (September), whose authors already run tau-bench retail with layer-wise counters. Both groups hold the tools; neither
has run the hosted-provider arm on a leaderboard harness, and the one published native-SDK-versus-third-party contrast on a hosted
frontier model (HarnessTax, $n = 80$) is null on average. So "why not done" is **the owners said they are doing it**, which from
the solo position is the race clause of Gate 6, not an opening. The complaint stream supports the mechanism and not the claim:
litellm's tracker carries 236 open-or-closed issues on `tool_calls anthropic`, among them documented translation faults on
tool-bearing requests — #44979 (2026-10-07) "`/v1/messages` drops `tool_result.is_error` when translating Anthropic → OpenAI tool
messages"; #51230 (2026-11-11) "`function.strict: true` is dropped when an OpenAI-format tool is sent to Anthropic"; #44029
(2026-10-01, closed) "streaming merges parallel tool_calls from one chunk into a single tool_use block"; #43156 (2026-09-25)
"Gemini tool translate maps empty arguments="" to args={"type":"object"} instead of {}"; #44946 and #43531 "`modify_params=True` drops adaptive `thinking` when
tool-call history has no thinking block". tau-bench's tracker has one litellm complaint (#34, 2025-02-13) and HAL's has #158 (the
Responses migration) and no translation complaint. Nobody in any tracker asks for the score comparison.

## 5. Killing experiment check

C-W46-03 as written: rebuild about 50 airline episodes' request streams, run litellm's provider transformations offline for
Anthropic, Google and Bedrock, run isloss, report the avoidable-loss share $L_p = \frac{1}{R_p}\sum_r \ell_r$ per provider $p$
over $R_p$ requests with $\ell_r \in \{0,1\}$. Cost holds at \$0 and 0 GPU-h for the Anthropic path — HAL's own monkey-patch of
`AnthropicConfig.transform_request` is proof that the offline transformation is a plain function call — but the Google path has no
offline arm: HAL sends Gemini OpenAI-format requests to Google's OpenAI-compatible endpoint, and the translation happens on
Google's servers, where isloss "cannot see" it; that arm needs isloss's "distinguishing conversations" (field-dependent prompts
whose answer reveals whether the field arrived), already run by isloss for this endpoint. The Bedrock path is not one HAL ships for
tau-bench. C-W46-04 (about \$300) is feasible but its "shipped litellm arm" stops being shipped the moment the user simulator is
pinned (the shipped harness leaves `gpt-4o` at the provider default, W45 lesson), its litellm version must be chosen because the
harness pins none, and its prior is HarnessTax's null at $n = 80$ with a 17-point interval; at 50 tasks and $k = 5$ the interval
on $\Delta$ is of that order, so the pre-registered kill (inside the replicate floor) is the expected outcome. Design hints had the
claim survived: name the translator version and `drop_params` state in the headline; split the Anthropic arm (offline oracle) from
the Google arm (behavioural probes); use 2611.04399's public per-record table and HAL's archive filenames to pick the model whose
archived rows exist, and report $\Delta$ on isloss-flagged versus clean tasks as the primary contrast, not the pooled gap.
